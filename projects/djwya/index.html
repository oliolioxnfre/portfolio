02

Why I built it

After getting into electronic music, my goal was to go to a real festival. But there are too many festivals, too many posters, and too many artists. I spent hours reading lineup posters for names I recognized, then digging through other artists' discographies to see if I'd even like the sound.

Electronic listening is wide and shallow: you're more likely to play one song each from 100 artists than ten songs each from ten. Dozens of artists I liked slipped past me on those posters. Most festival finders also cover only a fraction of the festivals that happen each year.

Tickets for the big ones start around $300 before travel, so I wasn't going to settle for a festival that didn't have it all: artists I like, genres I like, and a vibe I like. DJWYA treats taste as data so that choice is backed by numbers instead of marketing.

03

What it does

Sonic DNA

The core of DJWYA is a seven-axis model of how electronic music sounds: intensity, euphoria, space, pulse, chaos, swing and bass. Every subgenre gets a position in that space, and every artist inherits a profile from the genres they play.

Connect your library and your listening becomes a vector too. Every festival lineup gets a synergy score for how closely it matches you.

I placed the genres by hand, after listening to hundreds of them.

  • Sonic Universe

    An interactive D3 force-directed graph of electronic music, wiring hundreds of genres together by lineage. Genres can have several parents and children, so a tree wasn't enough. I researched where each style came from, and an LLM-assisted script helped fill in the edges.

  • Festival map

    Every festival in the database plotted worldwide with Leaflet, with clustering and geolocation, filterable by region, date and vibe. To get in, a festival has to be electronic or rock, have a set future date, and have a lineup of artists known to Spotify, SoundCloud or Last.fm.

  • Your taste, charted

    Dashboards built from your own library: a Sonic DNA star chart and genre distributions, generated by PostgreSQL queries over JSONB.

  • Crews

    The Crew Update finds the festival that best fits a group of two to eight friends at once.

  • Library import without Spotify's API

    Spotify locked its API down: an app can't have more than five users on Spotify sign-in until it has 250,000 active users. So playlists come in through Exportify, and Last.fm's listener-made tags classify the artists. Those tags turned out to be more accurate than Spotify's genres anyway.

  • Lineups from posters

    Scrapers find festival sites and lineup posters, then OCR and an LLM turn a flat image into structured rows in the database.

04

How it works

One Supabase Postgres database sits behind three components: a Next.js frontend on Vercel that reads under row-level security, a Python engine in Docker on Railway that scores festivals, and three scheduled scraper jobs on a repurposed ASUS Chromebox on my Tailscale network.

05

The scraper that failed quietly

Lineups are the hardest data to keep fresh, and the scrapers taught me the most. They went through a few homes before they were reliable:

  1. v1
    Agents in the homelab The first scrapers ran in Proxmox containers on my homelab: n8n, plus IronClaw, a fork of OpenClaw I picked for its security model. I couldn't get the two to cooperate, and poster search is repetitive anyway. So I dropped the agent for a plain automation workflow that was cheaper and more accurate.
  2. September
    18 days of silence I powered the homelab down for a few weeks. The scraper stopped, nothing told me, and I noticed 18 days later.
  3. fix
    Moved to the Chromebox The jobs became systemd timers on the Chromebox (MrChromebox firmware, Debian 13). Missed runs catch up at boot, every job has a timeout, and a healthchecks.io dead-man's switch alerts me if a run doesn't check in.
  4. days later
    Successful runs, almost no lineups Scrapes fell to nearly zero while every run still reported success. The failures were being recorded as "lineup not announced," which also pushed those festivals down the queue.
  5. telemetry
    One row per run, per festival, per network call The first instrumented run showed the cause. The search API key had hit its $5 spend cap, and the free fallback engines were blocking the box.
  6. now
    Outages look like outages Upstream failures leave the queue untouched, and a mostly-failed run exits with a distinct code so the alert fires. It runs unattended and tells me when a job fails, degrades or doesn't run at all.
06

Security & reliability

  • ✓
    Database grants. I revoked default execute rights on privileged functions and granted them back per caller. Column-level grants hide user emails and stop users from changing their own role. Before this, any signed-in user could make themselves an admin.
  • ✓
    Secrets. These live only in environment files and platform variables, none appear in Git history, and the deploy script never copies them.
  • ✓
    Found while writing this up. The scrapers sent a shared secret that the engine never checked. I deployed the check, set the secret on both sides, and committed two database migrations that had been applied but never recorded.
  • ○
    Next. CI and branch protection, since deploys currently run straight from main, plus scheduled key rotation.
07

What I'd do differently

DJWYA is my biggest project, and the one that exposed me to the most technology by far. I built it alone from February to October 2026. An AI coding assistant (Claude Code) wrote much of the code. I decided what to build, ran the infrastructure, and fixed what broke.

One cheap box is still a single point of failure: the alerting tells me when it's down but doesn't keep it up. Next time I'd build monitoring before the first outage, and keep every database change in version control from day one. The habit I took away is to check what's actually running before trusting the documentation, including my own.

What's next

I want every festival in the world on the map with a full lineup. Once the site is big enough, I'd like to release a standalone mobile app whose killer feature is mesh-network messaging, so you can find your friends at a festival even when the cell network is down.
