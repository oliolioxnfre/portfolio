Mojo Agent

A voice-first executive assistant I built and deployed for a client during my internship. It reads mail, drafts replies, and never sends anything without approval.

  •  Appenza internship
  • Jul–Aug 2026 · full-stack + deployment
  •  private repo
01

What it is

My internship at Appenza wasn't the coffee-run kind. I joined as the full-stack engineer on one of their new startup ideas: Mojo, a real-time, voice-first executive assistant. The first client was the Head of Office at OBMMS.

Mojo reads his mail, briefs him each morning, drafts replies, and takes instructions by voice. Mail, Teams chats and WhatsApp Business messages feed a memory graph of the people, projects and companies he deals with. One rule drove the whole design: it never sends anything he hasn't approved.

My boss laid out the product. I built it, made the architecture and security decisions, ran the deployments, and worked with the OBMMS team to fit it to how their office actually runs. I built it with Claude Code: it wrote much of the implementation, and I reviewed, tested and debugged it.

02

The IT side

Shipping software into a real office turned out to be half IT work:

  • Check DNS first

    The plan assumed Microsoft Graph for mail and calendar. An MX lookup showed the domain's mail was on Hostinger, and Graph wouldn't work without Microsoft 365 licences. I should have run that lookup before designing anything.

  • Domain migration

    I worked with the OBMMS IT team on moving the domain's mail off Hostinger. It was the roughest stretch of the internship.

  • Server administration

    I ran the production server, a Frankfurt VPS running Coolify and Docker. It has no public ingress and is reachable only over Tailscale.

  • Endpoint setup

    I set up Tailscale on the client's laptop, so the server never needed a public address.

  • Desk-side support

    I also became the office's go-to for IT: installing software on their computers and helping whenever an IT issue came up.

  • Least privilege

    I was offered admin access to everything. I declined and took one mailbox credential, the minimum the assistant needed.

03

How it works

A Next.js app and a Python sidecar run under Coolify on the VPS. Postgres is the system of record for drafts, approvals and the audit log. FalkorDB holds the relationship graph that the Graphiti sidecar builds, and it can be rebuilt from Postgres. Mail moves over IMAP and SMTP.

Voice audio goes directly between the laptop and OpenAI. The server only issues a short-lived key and runs the tool calls, so it never handles the audio stream.

04

The reply that never sent

In a rehearsal, an approved reply never went out, and the assistant kept saying it was "still processing." I fixed three plausible causes before I read the evidence I already had:

  1. fix 1
    Port 465 was blackholed That network silently dropped traffic to SMTP port 465, so I moved to 587.
  2. fix 2
    Hanging instead of failing The send had hung rather than erroring, because no timeouts were set. I added them.
  3. fix 3
    A stranded draft The failure left the draft marked approved but unsent, and invisible to the queue. A failed send now returns the draft to pending and records why.
  4. still broken
    Reading the audit log properly Mail still didn't leave. The audit log had said it all along: "No recipients defined." nodemailer doesn't derive the SMTP envelope from a raw message's headers, so I built both from one recipient list. That fixed it.
  5. now
    The health check logs in The health check now verifies the SMTP login too, so a broken send path shows up before someone approves a reply.
05

Security & reliability

  • ✓
    Approval in the database. The no-send-without-approval rule is enforced by a Postgres trigger, not application code, and tests attack five ways around it.
  • ✓
    Narrow access. One mailbox credential instead of admin access to everything, and a server reachable only over Tailscale.
  • ✓
    Secrets. API keys are encrypted with AES-256-GCM in the database, not kept in files. A PIN with escalating lockouts guards the app and its API routes.
  • ✓
    Internal services stay internal. The graph database and the sidecar publish no ports.
  • ✓
    Data handling. Model calls carrying his mail are refused if the provider's terms allow training on it.
  • ○
    Next. A CI gate, since a push to master deploys directly. Open the mailbox read-only, with a test for the no-delete rule. And a named owner for the VPS.
06

What I'd do differently

My internship ended before the project did. When I left, reading mail, sending approved replies and voice approval all worked. I don't know whether it's in daily use.

I'd separate the development and production databases from day one: twice, the test suite wiped live data. I'd check DNS before designing anything. And when something breaks, I'd read the logs I already have before fixing the causes I can imagine.

What I took away

How to run a real service on infrastructure I administered, with access kept as narrow as the job allowed.
